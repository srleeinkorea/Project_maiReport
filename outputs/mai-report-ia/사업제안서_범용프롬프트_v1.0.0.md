# 사업 제안서 범용 프롬프트

개념도 한 장 + 제안서용 기획서 한 벌을 같은 품질로 뽑아내기 위한 프롬프트입니다.
`[ ]` 안만 사업에 맞게 채워서 그대로 붙여 넣으면 됩니다. 비워 두면 Claude가 묻습니다.

---

## 1. 붙여 넣을 프롬프트

```
너는 UI/UX 설계 전문가이자 국책과제를 여러 번 수주한 시니어 PM이다.
아래 사업을 심사위원이 5분 안에 이해하고 "이건 돌아가겠다"고 느끼도록
① 개념도 한 장과 ② 제안서에 바로 옮겨 쓸 기획서를 만들어라.

## 사업 정보
- 사업명: [예: AI 기반 지역사회 통합 환자 여정 시스템]
- 한 줄 요약: [예: AI가 일상 건강관리와 지역 진료를 하나의 흐름으로 연결한다]
- 주 사용자: [예: 70대 이상 어르신 / 보호자 / 경로당 관리자 / 의료진]
- 지금의 문제: [예: 기관마다 기록이 따로 있어 어르신이 소견서를 들고 다녀야 한다]
- 바꾸려는 것: [예: 기록이 사람을 따라가고, 앱이 다음 할 일을 알려 준다]
- 구성 단계/참여 주체: [예: 1단계 경로당 → 2단계 보건소 → 3단계 2차병원 → 4단계 3차병원]
- 가운데서 잇는 것: [예: 개인 건강관리 앱 + AI 연결 허브]
- 단계별 쓰는 기술: [예: 안저 AI, 심전도 AI, 초음파 AI, MRI AI …]
- 사업 기간/규모: [예: 3년, 시범 지역 1곳 → 2곳]
- 꼭 반영할 제약: [예: 법무 회신 — 동의 2개 분리, 본인확인 정보는 서버 경유]
- 참고 자료: [첨부 파일, 기존 그림, 회신 문서 등]

## 산출물 1 — 개념도 (SVG + PNG)
- 단계는 왼쪽→오른쪽 한 줄. 읽는 순서가 헷갈리는 원형·지그재그 배치 금지.
- 단계 사이 화살표는 방향별로 뜻을 나눠라(예: 위로 보냄 / 되돌려 보냄). 범례를 붙여라.
- 가운데 잇는 것(앱·플랫폼·허브)은 띠 하나로 묶고, 모든 단계가 거기에 연결되게 그려라.
- 각 단계 카드: 번호 · 이름 · 부제 · 역할 한 줄 · 하는 일 3개 · 쓰는 기술(이름 + 하는 일 한 줄).
- 기술은 이름만 나열하지 말고 "무엇을 해 주는지"를 어린이도 알 말로 옆에 써라.
- 그림 아래에 실제 한 사람의 여정 예시 4~5칸을 넣어라. 올라갔다가 다시 돌아오는 흐름을 보여라.
- 맨 아래 흐름 띠는 마지막에 "다시 [일상/지역]으로"를 넣어 끝이 아니라 순환임을 보여라.
- 톤앤매너: 고급스럽고 신뢰감 있게. 짙은 남색을 기본으로 두 계열(일상 쪽·전문 쪽)을 구분하고
  포인트는 한 가지 금속 톤만. 바탕은 순백 대신 아주 옅은 아이보리. 카드 테두리는 얇게, 그림자는 약하게.
- 글자는 Noto Sans KR. 파일은 SVG(수정용)와 2배 해상도 PNG(삽입용) 둘 다.
- 그리고 나서 렌더링한 결과를 직접 보고 글자 넘침·화살표 겹침·모서리 삐져나옴을 고쳐라.

## 산출물 2 — 기획서 (HTML 한 파일)
아래 장을 이 순서로. 각 장은 처음 보는 사람 기준으로, 실제 예시를 반드시 하나 이상 넣어라.
1. 왜 필요한가 — 지금 벌어지는 일(사례) / 이 사업이 바꾸는 것 / 한 줄 요약
2. 개념도 — 그림 삽입 + "그림 읽는 법" 4줄
3. 단계별 정의 — 표: 단계 · 기관 · 맡는 일 · 현장의 사람 · 쓰는 기술 · 남는 기록
4. 연계 규칙 — 언제 위로 보내고 언제 되돌리는지 / 보낼 때 반드시 같이 가는 것 / 기준은 전문가가 정한다는 원칙
5. 핵심 플랫폼 설계 — 하는 일 4가지 / 보는 사람별 화면 / 핵심 화면 3장(구조만)
6. 주 사용자 기준 UX 원칙 — 표: 원칙 · 이렇게 한다 · 이렇게 하지 않는다 + ❌/⭕ 문구 예시
7. 예시 여정 — 한 사람의 흐름을 단계별로, 각 단계에서 플랫폼이 무엇을 했는지
8. 정보 흐름과 동의 — 표: 기록 · 만드는 곳 · 보는 곳 · 동의 단위 + 제약 사항 반영
9. 성과지표 — 표: 지표 · 무엇을 재는가 · 왜 중요한가. 핵심 지표는 2개만 고르라고 권고
10. 추진 체계와 일정 — 역할 분담 표 + 연차별 4칸. "먼저 작은 것이 돌아가야 다음을 붙인다" 원칙
11. 위험과 대응 — 표: 위험 · 무슨 일이 생기나 · 대응
12. 바뀐 내용 — 날짜 · 항목 · 바뀐 것 · 어디

## 쓰는 규칙
- 초등학생도 이해할 말로. 내부 식별자·영문 변수명·약어 금지. 전문 용어는 괄호로 풀어라.
- 작성자 이름, QA 체크리스트, 검수 서명란은 넣지 않는다.
- 문서 본문에 색상 값·색 이름을 적지 않는다(디자이너 영역). 그림은 예외.
- 무서운 말(위험·의심·확률 숫자)을 사용자에게 직접 보여 주는 문구는 쓰지 않는다.
- 수치 기준(임계값 등)은 "전문가 자문으로 확정"이라 적고 임의로 확정하지 않는다.
- 발행 상태는 문서 안에 "v1.0.0 · 날짜"로. 파일 이름의 버전은 올리지 않는다.
- 파일 이름: [프로젝트]_[문서명]_v1.0.0.html / .svg, PNG는 버전 없이.
- 끝나면 같은 폴더에 저장하고, 작업 단위로 한 번에 커밋하라.
- 마지막에 내가 확인해야 할 것(임의로 만든 사례, 가정한 수치)을 2~3개로 정리해 물어라.
```

## 2. 쓰는 요령

- **사업 정보 11칸 중 「지금의 문제」와 「바꾸려는 것」이 제일 중요합니다.** 이 두 줄이 1장과 한 줄 요약, 성과지표까지 결정합니다. 비워 두면 평범한 문서가 나옵니다.
- **기존 그림이 있으면 첨부하고 "이 그림 보완해줘"로 시작**하세요. 처음부터 그리는 것보다 빠르고 원래 의도가 보존됩니다.
- 결과물이 나오면 **「예시 여정」의 사례와 「연계 규칙」의 수치**부터 확인하세요. Claude가 만든 가상 사례라 실제 시나리오로 바꿔야 할 가능성이 큽니다.
- 다른 분야(교육·농업·안전 등)에 쓸 때는 「단계/참여 주체」와 「가운데서 잇는 것」만 바꾸면 나머지 구조는 그대로 맞습니다.
