maiReport 데이터 흐름도 · 저장소 기준 (Level-1 DFD) 2026-09-11
Data Flow · Store View

어떤 테이블에
누가 쓰고 누가 읽는가.

기존 서비스 데이터 흐름도 v0.1(09-08)은 지식이 해석을 거쳐 화면이 되는 개념 흐름을 그렸습니다. 이 문서는 같은 서비스를 저장소 기준으로 다시 세웁니다 — 외부 입력, 처리, 데이터 저장소를 노드로 놓고 각 흐름에 이름을 붙였습니다. 그러면 개념도에서는 보이지 않던 것이 드러납니다: 질문은 파이프라인의 시작이 아니라 되먹임이고, 지표 계산은 두 갈래인데 한 갈래가 통째로 비어 있으며, 목표 기록 저장소가 없습니다.

01

흐름도

세 개의 띠는 서로 다른 생애주기를 가집니다. 지식은 release 단위로 통째 교체되고, 생활 데이터는 매일 쌓이며, 상호작용은 하루 단위로 리셋됩니다. 결제 · 분석 이용권은 홈 네 축과 데이터를 주고받지 않아 제외했습니다.

읽는 순서

① 생활 데이터로 지표를 만든다 → ② 규칙 평가와 목표 개인화를 일단 돌린다 → ③ 결과가 불충분하면 부족분만큼 문항을 고른다 → ④ 답변이 쌓이면 ②를 다시 돈다. 질문이 화면 맨 위에 있다고 해서 파이프라인의 시작인 것은 아닙니다.

02

저장소 목록 — 누가 쓰는가

저장소마다 쓰기 주체가 하나뿐인지 확인하는 것이 이 표의 목적입니다. 쓰기 주체가 불분명한 저장소는 동시성·정합성 문제가 먼저 생깁니다.

저장소쓰기읽기생애주기상태
D1coaching_* 5종 P1 (오프라인 적재)P5 release 단위 교체정의됨

읽는 곳이 셋인 저장소

health_sample은 P3(3지표) · P3b(코칭 지표) · P4(결측 현황) 셋이 읽습니다. 생활 데이터는 컨디션 전용이 아닙니다 — 코칭과 질문도 여기서 읽어 갑니다. 다만 P3b의 산출물을 담을 저장소가 없어, 코칭용 지표는 요청마다 즉석 계산하거나 새 저장소를 두어야 합니다. 어느 쪽인지 정해야 합니다.

범위 밖

결제 · 분석 이용권(purchase · analysis_ticket)은 셀비 체크업 / ANRISK 전용 도메인이라 이 흐름도에서 제외했습니다. 홈 네 축과 데이터를 주고받지 않습니다. 해당 도메인은 maiReport_데이터모델_v1.0.0.html 4~5장이 이미 상태 전이까지 정의하고 있습니다.

03

개념도에서는 보이지 않던 것

저장소를 노드로 세우자 드러난 항목입니다. 기존 서비스 데이터 흐름도 v0.1과 대조한 결과입니다.

항목개념도 v0.1저장소 기준에서 드러난 것
목표 축 없음 — 출력이 “3지표 + 행동 1개” D7이 통째로 비어 있다. 완료·쉬기 기록, 주간 달성률, 연속일수의 저장 구조가 어느 문서에도 없다
질문 축 수집 항목의 하나로만 등장 질문은 파이프라인의 입력이 아니라 되먹임이다. 코칭·목표를 먼저 돌려 부족분을 안 뒤, 그만큼만 문항으로 바꿔 되묻는다 — 최대 3문항은 상한이지 정원이 아니다
지표 → 코칭 “통과한 지표값”이 그대로 흐름 지표 계산이 두 갈래로 갈라진다 — 화면용 3지표(P3)와 코칭 판정용 지표(P3b)는 같은 health_sample을 읽지만 다른 것을 만든다. D4는 코칭에 쓰이지 않으며, P3b는 아직 없다
질문 ← 생활 데이터 질문이 수집 항목으로만 등장 결측 보완형 문항은 무엇이 비었는지 읽어야 고를 수 있다. 현재 구현은 의료이력 유무만 본다
기본 목표 세트 없음 카드 문구의 원본이 프로토타입 하드코딩에만 있다. 카탈로그로 올릴지 미정
목표만 다르다 — 화면 문구가 틀렸다

질문과 코칭은 생활 데이터를 읽지만 목표는 읽지 않는 것이 설계입니다. 정책 메모가 목표 분석을 두고 “목표·실천 기록은 수동. 기기 불필요”라고 못 박았고, 개인화 로직도 질문 답변만 봅니다.

그런데 홈 화면의 목표 카드 부제는 답변 전 상태에서 “현재 건강 데이터를 바탕으로 추천한 목표예요”라고 말합니다. 읽지 않는 데이터를 근거로 제시하고 있으므로, 흐름이 아니라 문구를 고쳐야 합니다 — 예: “먼저 추천하는 기본 목표예요”.

추가로 발견한 이름 불일치

지표 이름이 문서 세 곳에서 각각 다릅니다 — 데이터 모델 v0.1은 recovery · load · rhythm(회복여유·생활부담·리듬안정성), 서비스 데이터 흐름도 v0.1은 생활여유 · 건강돌봄 · 일상안정, 지표 기획서 v0.3은 생활여유 · 자기돌봄 · 일상안정입니다. 같은 날(09-08) 나온 두 문서가 가운데 지표를 ‘건강돌봄’과 ‘자기돌봄’으로 다르게 부르고 있습니다.

04

이 흐름도가 요구하는 결정

결정내용막히는 것
D7 스키마 목표 기록을 카테고리 × 일자로 저장하는 테이블 정의. 완료·쉬기·잠금 상태와 연속일수 포함 오늘의 목표 · 주간 목표 분석 전체
P3b 코칭 지표 계산 health_sample에서 코칭 계약의 :metrics를 직접 계산하는 처리. 결과를 저장할지(새 저장소) 요청마다 계산할지도 함께 결정 코칭 239건 중 지표 기반 전부
P4 결측 판정 문항 선택이 수집 현황을 읽도록 구현. 현재는 의료이력 유무만 분기 결측 보완형 문항의 실효성
목표 카드 부제 수정 “현재 건강 데이터를 바탕으로” → 기기 데이터를 읽지 않으므로 문구 교체 화면 문구와 설계의 불일치
지표명 통일 세 문서의 이름을 하나로. metric_score.metric_key 값까지 함께 교체 화면 · 데이터 모델 · 흐름 문서
기본 목표 세트 위치 D1 계약에 넣을지, 별도 카탈로그로 둘지, 앱 상수로 남길지 목표 문구 운영 · 버전 관리
