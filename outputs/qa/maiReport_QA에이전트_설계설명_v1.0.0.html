1배경 — 이 프로젝트에서 QA가 확인하는 것

maiReport는 건강검진 결과와 매일의 생활 기록을 바탕으로 한 사람에게 맞는 작은 건강 목표를 내주는 서비스입니다. 이 저장소는 그 서비스의 기획 저장소입니다. 기획팀은 여기서 개발자에게 넘길 세 가지를 만듭니다.

기획 산출물쉽게 말하면식이 기능의 예
데이터 계약 (엑셀)개발자가 그대로 옮겨야 하는 약속. 질문·문구·규칙이 표로 적혀 있습니다.질문 9개, 목표 문구 172개, 확정 규칙 9개, 검증규칙 49개
참조 코드규칙이 실제로 돌아가는 견본. 개발자는 이걸 보고 서비스 코드를 짭니다.목표 단계 계산, 끼니 시각 판정, 질환별 금지 문구 거르기
개발 안내 문서계약을 사람 말로 풀어 쓴 설명.식이 구현점검 문서

식이 기능은 이렇게 움직입니다. 사용자는 앱을 열 때 식사 질문 최대 2개에 답하고, 목표 하나를 받습니다. 목표에는 시작 → 기본 → 도전 세 단계가 있어서, 일주일 안에 세 번 해내면 한 단계 오르고 두 번 연속 못 하면 한 단계 내려갑니다.

QA가 묻는 질문은 하나입니다. 「참조 코드와 데이터가, 계약에 적힌 규칙대로 되어 있는가?」 여기서 틀리면 개발자가 틀린 견본을 그대로 옮기고, 사용자에게 틀린 목표가 나갑니다.

2풀려던 문제 — 테스트가 다 통과했는데 버그가 있었다

식이 기능에는 이미 테스트 29개가 있었고, 전부 통과했습니다. 그런데 10월 7일에 계약서를 한 줄씩 대조해 보니 이런 일이 생겼습니다.

장면 민수 씨는 짠 음식을 줄이는 목표가 잘 안 돼서, 앱이 그 영역을 「개선 필요」로 보고 있습니다. 계약에는 「개선 필요인 영역은 기본 단계까지만 올린다」고 적혀 있습니다. 가장 어려운 목표를 주면 실패하고 내려가기를 반복하기 때문입니다.
그런데 민수 씨가 사흘 연속 목표를 해내자, 참조 코드는 그를 도전 단계로 올렸습니다.

테스트 29개가 이걸 못 잡은 이유는 단순합니다. 테스트를 코드 작성자가 썼고, 작성자가 그 규칙을 코드에 넣지 않았으니 테스트에도 없었습니다. 작성자가 쓴 테스트는 작성자가 이해한 만큼만 확인합니다.

이 문제는 한 번은 사람이 손으로 대조해서 찾았습니다. 하지만 그 방식에는 네 가지 약점이 있었습니다.

  1. 방법이 사람 머릿속에 있습니다. 다른 팀원이 수면 기능을 검증하려면 처음부터 다시 생각해야 합니다.
  2. 다시 돌리기 어렵습니다. 그날 쓴 확인 스크립트는 그 문제 두 개만 위한 것이라, 코드를 고친 뒤 같은 확인을 반복하려면 스크립트를 찾아 고쳐야 합니다.
  3. 얼마나 확인했는지 안 보입니다. 문제 5건을 찾았다는 건 알지만, 규칙 58개 중 몇 개를 봤고 몇 개를 안 봤는지는 보고서에 없습니다.
  4. 판정 기준이 사람마다 다릅니다. 무엇이 「높음」이고 언제 「출시 보류」인지 정해 둔 것이 없었습니다.

QA 에이전트는 이 네 가지를 해결하려고 만들었습니다.

3설계 원칙과 그 근거

여섯 가지 원칙을 정하고 모든 구성 요소가 이를 따르게 했습니다. 각 원칙 아래 상자가 근거입니다.

P1

정답지는 코드 밖에 하나만 둔다

기대값(이렇게 나와야 한다)은 데이터 계약과 확정 규칙에서만 가져옵니다. 대상 코드를 읽고 기대값을 정하지 않습니다.

근거29개 테스트가 모두 통과했는데 높음 문제가 3건 있었습니다. 코드에서 기대값을 뽑으면 버그가 정답이 됩니다. 소프트웨어 테스트에서는 이 정답 출처를 「오라클(판정 기준)」이라 부르고, 검증 대상과 떨어져 있어야 한다는 것이 기본 원칙입니다.
P2

규칙에서 출발하고, 규칙마다 검증을 연결한다

계약에 적힌 규칙 번호(예: V-42)를 케이스마다 붙입니다. 보고서는 규칙 58개를 모두 나열하고, 각 규칙에 어떤 검증이 연결됐는지, 아무것도 없으면 「미검증」이라고 보여 줍니다.

근거「통과」는 무엇을 확인했는지와 함께 있어야 뜻이 있습니다. 규칙 5개만 보고 통과한 것과 58개를 보고 통과한 것은 다릅니다. 이 표를 「요구사항 추적표」라고 하며, 의료·금융처럼 규칙이 많은 분야의 QA에서 표준으로 씁니다. 다음 회차에 무엇부터 할지도 이 표의 빈칸이 알려 줍니다.
P3

생각은 AI가, 판정은 실행기가 한다

AI 에이전트는 규칙을 읽고 케이스를 설계하고 실패 원인을 분류합니다. 하지만 「통과/실패」는 AI가 말로 정하지 않고, 실행기가 실제로 함수를 불러 기대값과 비교해서 정합니다.

근거AI가 「확인해 보니 맞습니다」라고 쓴 것은 증거가 아닙니다. 같은 계획 파일을 누가 언제 돌려도 같은 결과가 나와야 믿을 수 있습니다. 그래서 보고서에는 계약 파일의 지문(내용으로 만든 고유값)을 찍어, 어떤 판의 계약으로 돌린 결과인지 남깁니다.
P4

검증자는 고치지 않는다

에이전트는 제품 코드, 계약 엑셀, 기획 문서를 읽기만 합니다. 쓰는 곳은 계획 파일과 결과 폴더뿐입니다. 고칠 방법은 보고서의 「제안」으로 적습니다.

근거고치는 사람과 검사하는 사람이 같으면, 검사가 고친 쪽에 맞춰지는 일이 생깁니다. 또 「관찰 중인 영역은 단계를 안 올린다」를 코드에 어떻게 넣을지는 개발의 결정이고, 규칙이 애매할 때 어느 쪽이 맞는지는 기획의 결정입니다. QA가 대신 정하지 않습니다.
P5

모르는 것은 모른다고 쓴다

확인하지 않은 범위는 「이번에 확인하지 않은 것」에, 정책이 애매한 것은 「정책 확인이 필요한 것」에 따로 적습니다.

근거식이 계약은 목표를 고를 때 「유효 답 수 → 마지막 질문일 → ID 순」으로 정렬하라고 적었지만, 참조 코드는 「개선 필요 영역 먼저」를 추가로 씁니다. 어느 쪽이 의도인지는 문서만으로 알 수 없습니다. 이럴 때 한쪽을 정답으로 정해 버리면, QA가 정책을 몰래 정하는 셈이 됩니다.
P6

처음 보는 사람이 읽히게 쓴다

케이스마다 규칙을 한 문장으로 쓴 제목과, 사람이 나오는 장면을 붙입니다. 「currentStage=BASE, axisState=NEEDS_WORK」가 아니라 「민수 씨의 짠맛 영역은 개선 필요이고…」로 씁니다.

근거보고서를 읽고 결정하는 사람에는 기획자, 디자이너, 의학팀이 있습니다. 코드값만 있는 보고서는 개발자만 읽을 수 있고, 그러면 「이게 정말 문제인가?」를 판단할 사람이 줄어듭니다.

4식이 기능에 적용한 예시

아래는 실제 실행 결과입니다. 버튼을 눌러 케이스를 바꿔 보세요. 같은 규칙(V-42, 목표 단계 변경)에서 나온 케이스가 어떤 것은 통과하고 어떤 것은 실패하는지 볼 수 있습니다.

입력
계약대로라면
참조 코드가 실제로 낸 값

이번 회차에 찾은 것

심각도무엇이 문제인가어떻게 찾았나
높음「관찰 중」인 영역(아직 답이 적어 상태를 모름)도 사흘 해내면 단계가 오른다함수를 실제로 불러 봄
높음「개선 필요」인 영역이 「도전」까지 오른다 (2장의 민수 씨)함수를 실제로 불러 봄
높음오늘 질문은 「물 마시기」인데 목표는 다른 영역에서 나올 수 있다. 목표를 고르는 함수가 오늘 질문을 입력으로 받지 않는다코드 읽기 (입력 자리가 없어 실행으로는 못 보임)
보통계약서에 적힌 필드 이름으로 넘기면 결과가 달라진다 (계약은 state_code, 코드는 status_code)두 입력을 넣고 결과 비교
보통계약 규칙 R-05는 「식후 목표 후보 10개」라고 쓰는데 데이터는 13개다. 개발자가 10을 그대로 박으면 3개가 빠진다문서 숫자와 데이터 대조
낮음개발 안내 문서의 질문 수(8)·선택지 수(24)·문구 수(143)가 현재 계약(9·27·172)과 다르다문서 숫자와 데이터 대조

판정은 보류입니다. 높음이 하나라도 있으면 보류로 정해 두었기 때문입니다. 반대로 경계값(만료일 당일·다음날·말일), 하락 규칙, 소급 완료 제외 같은 12개 케이스는 통과했고, 데이터 무결성 점검 14개도 모두 통과했습니다. 이건 「확인해서 맞았다」는 증거로 남습니다.

5구조와 6단계 절차

QA 에이전트는 네 부분으로 나뉩니다. 바뀌는 것은 계획 파일 하나뿐이고, 나머지는 모든 기능이 같이 씁니다.

부분파일왜 따로 뒀나
절차.claude/skills/feature-qa/SKILL.md사람이 하든 AI가 하든 같은 순서를 밟게 하려고. 팀의 QA 방법이 문서 한 장에 고정됩니다.
역할.claude/agents/feature-qa.md검증자의 권한(읽기 전용)과 보고 형식을 정해, 여러 기능을 나눠 맡겨도 같은 품질이 나오게.
실행기qa-agent/bin/qa.mjs판정을 기계가 하게(P3). 설치할 패키지가 하나도 없어 Node만 있으면 누구나 돌립니다.
계획 파일qa-agent/plans/<기능>.qa-plan.json기능별로 바뀌는 것은 여기에만. 회차마다 케이스가 쌓여 회귀 묶음이 됩니다.

6단계 절차

  1. 범위 잡기

    어느 폴더를 무엇에 대고 확인할지, 이번에 안 볼 것은 무엇인지 정합니다. qa.mjs init이 폴더를 훑어 테스트·계약·함수 목록을 보여 줍니다.
    산출물: 계획 뼈대, 범위사람: 대상 폴더 확인

  2. 규칙 뽑기

    계약의 규칙을 하나씩 읽고 확인 방법을 고릅니다. 데이터 모양이면 데이터 점검, 함수 동작이면 시나리오, 함수에 입력 자리가 없으면 코드 읽기, 서버·화면이 필요하면 범위 밖.
    산출물: 규칙 추적표의 뼈대

  3. 케이스 설계

    규칙 하나에 정상 1개와 경계 1개 이상. 예: 「검진 결과는 3개월 유효」면 7/7→10/7(만료일 당일, 유효), 7/6→10/7(하루 넘김, 무효), 11/30→2/28(말일) 세 개.
    산출물: cases · dataChecks · findings

  4. 실행

    qa.mjs run 한 줄. 기존 테스트 → 데이터 점검 → 시나리오 → 규칙 추적 → 판정 순으로 돕니다.
    산출물: 보고서, 결과 기록

  5. 원인 분류

    실패마다 셋 중 하나로 가릅니다. 이 단계를 건너뛰면 보고서에 가짜 실패가 섞입니다.
    케이스가 틀렸다입력 형태 실수, 기대값을 잘못 적음 → 계획을 고쳐 다시 실행
    대상이 틀렸다코드가 계약과 다름 → 실패로 보고, 위치와 제안을 적음
    기준이 애매하다문서끼리 다르거나 해석이 둘 → 정책 질문으로 올림
    사람: 정책 질문에 답

  6. 보고와 인계

    판정 한 줄, 고칠 것(심각도 순), 정책 질문, 미검증 규칙 수를 전합니다. 계획 파일은 지우지 않고 남겨 다음 회차의 출발점으로 씁니다.
    산출물: QA보고서.html · QA요약.md

조건부 통과보통·낮음 실패만 있음보통 계약과 다르게 동작하거나 개발자를 헷갈리게 하는 계약 내부 불일치
통과계획한 항목이 모두 계약과 일치낮음 동작에 영향 없는 문서 숫자·표기 오류

「통과」는 계획한 범위 안에서 통과라는 뜻입니다. 그래서 보고서는 판정 옆에 「규칙 중 검증이 연결된 것 24/58」을 항상 함께 보여 줍니다.

6이렇게 설계해서 좋아진 점

같은 식이 기능을 두 방식으로 QA한 결과를 나란히 놓았습니다.

항목사람이 손으로 (1차)QA 에이전트
다시 돌리기그날 쓴 스크립트를 찾아 고쳐야 함명령 한 줄. 개발자가 코드를 고치면 같은 케이스가 그대로 다시 확인
확인 범위찾은 문제만 보임규칙 58개 중 24개 연결, 34개 미검증이 목록으로 보임
확인한 케이스재현 3개시나리오 17개 + 데이터 점검 18개 + 코드 읽기 1건. 통과한 것도 증거로 남음
판정「계약 전체를 준수한다고 판정할 수 없다」「보류 — 높음 3건」. 같은 조건이면 누가 돌려도 같은 판정
보고서 독자개발 용어 위주의 서술케이스마다 장면 문장 + 규칙 원문 + 입력·기대·실제 나란히
새로 찾은 것—계약 안의 규칙 R-05(「10개」)와 데이터(13개)가 서로 다름
필요한 도구Python과 엑셀 읽기 패키지Node 하나. 설치할 패키지 없음
다른 기능에 적용처음부터 다시 설계같은 절차, 같은 실행기. 계획 파일만 새로 씀

정리하면 세 가지입니다. 믿을 수 있고(정답지가 코드 밖에 있고 판정을 기계가 함), 얼마나 믿을지 보이고(규칙 추적표), 쌓입니다(계획 파일이 회차마다 두꺼워져, 고친 문제가 다시 생기면 바로 잡힘).

7다른 기능으로 넓히기

같은 모양의 기능: 활동·수면·기타

maiReport의 「오늘의 질문」은 식이·활동·수면·기타 네 영역으로 나뉠 예정이고, 네 영역 모두 「질문 → 영역 상태 → 단계별 목표」라는 같은 뼈대를 씁니다. 그래서 식이 계획 파일이 그대로 본보기가 됩니다. 팀원이 수면 기능을 맡으면 이렇게 시작합니다.

node qa-agent/bin/qa.mjs init 수면 --target outputs/mai-report-policy/수면
node qa-agent/bin/qa.mjs extract outputs/mai-report-policy/수면/<계약>.xlsx --sheet 검증규칙
#  → 규칙마다 케이스를 채운 뒤
node qa-agent/bin/qa.mjs run qa-agent/plans/수면.qa-plan.json

Claude Code에서는 /feature-qa 수면 한 줄로 같은 절차가 시작됩니다. 식이에서 만든 「단계는 7일 안 3회 완료로 오르고 2회 연속 미완료로 내린다」 같은 케이스는 수면 계약에 같은 규칙이 있으면 입력만 바꿔 옮겨 쓸 수 있습니다.

모양이 다른 기능: 지표·결제·알림

참조 코드가 없고 기준표만 있는 기능도 데이터 점검만으로 시작할 수 있습니다. 예를 들어 또래 등수 기능은 퍼센타일 기준표가 핵심이라 「연령대·성별마다 행이 빠짐없이 있다」(묶음별 개수), 「백분위 값이 0~100 사이」(허용 범위) 같은 점검이 바로 들어갑니다. 필요한 점검 종류가 없으면 실행기의 점검 목록에 함수 하나를 더하면 모든 기능이 같이 씁니다.

같은 기대값, 확인하는 곳만 바꾼다

확장의 핵심은 이것입니다. 계획 파일의 규칙과 기대값은 그대로 두고, 어디에 대고 확인하느냐만 바꿉니다. 「개선 필요인 영역은 기본까지만 오른다」는 참조 코드에서도, 실제 서버에서도, 앱 화면에서도 같아야 하기 때문입니다.

HTML 프로토타입을 브라우저로 열어 「사흘 완료」를 눌러 보고 화면에 나온 단계를 기대값과 비교.

서비스 개발 후
실제 서버

같은 케이스의 입력을 서버 API에 보내고 응답을 비교. 기획 단계에서 만든 케이스가 그대로 서비스 검수 기준이 됩니다.

운영
자동 실행

계약 엑셀이 바뀔 때마다 자동으로 돌려, 보류(종료 코드 1)면 배포를 막습니다.

팀원이 처음 적용할 때

  1. Node 20 이상을 설치합니다. 이 저장소를 받으면 절차·역할·실행기가 함께 들어옵니다.
  2. 식이 계획 파일(qa-agent/plans/식이.qa-plan.json)과 그 보고서를 한 번 읽습니다.
  3. 내 기능 폴더로 init을 돌리고, 기준 문서 하나를 정답지로 정합니다.
  4. 심각도 높음이 될 규칙(사용자 안전, 단계·자격 판정)부터 케이스를 씁니다.
  5. 돌리고, 실패를 세 갈래로 분류하고, 정책 질문은 기획 담당에게 넘깁니다.

8한계

  • 기준 문서가 틀리면 함께 틀립니다. 정답지가 계약이므로, 계약에 잘못 적힌 규칙은 걸러내지 못합니다. 문서끼리의 숫자 차이는 잡지만 규칙의 의학적 타당성은 의학팀 검수 범위입니다.
  • 코드 읽기 발견은 AI의 판단입니다. 그래서 근거 코드와 줄 번호를 반드시 붙이고, 입력 자리가 생기면 실행 케이스로 바꾸도록 절차에 적었습니다.
  • 지금은 참조 코드와 데이터만 봅니다. 서버 저장, 재진입, 중복 요청, 화면 동작은 7장의 확장 단계입니다. 보고서의 「이번에 확인하지 않은 것」에 매번 적힙니다.
