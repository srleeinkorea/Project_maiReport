# 식이 구현 기준 — v1.0.0

## 적용 범위

이 폴더의 데이터 계약 엑셀이 개발 기준이다. `diet-selection-v1.0.0.mjs`는 날짜·답변 재사용·식후 후보 판정, `diet-profile-condition-v1.0.0.mjs`는 수동 질환·진료정보 집계, `diet-goal-engine-v1.0.0.mjs`는 출처별 후보 이동·검진 3개월 유효기간·목표 단계 변경의 실행 가능한 참조 코드다. 실제 서버 저장과 검진 원본 판정은 서비스 구현에서 이 계약에 연결한다.

앱은 개인 처방식과 식품 알레르기 정보를 수집하지 않는다. 따라서 두 정보를 이용한 개인화 판정은 계약에 두지 않는다. 일반 식품 목표 문구는 질환별 금지, 앱 진입 시각, 현지 요일, 백엔드가 전달한 대한민국 명절·연휴 날짜에 따라 사용한다. 배달·편의점·회식처럼 앱이 확인하지 않는 상황 조건은 사용하지 않는다.

## 내정보의 만성질환 직접 입력

공개 프로토타입의 **더보기 → 내정보 → 만성질환**에는 진료정보 연동과 별도로 4개 질환을 직접 선택하는 화면이 있다. 수동 선택은 `SELF_REPORTED`로 저장하고 진료정보의 후보·사용자 확인·부정 기록을 덮어쓰지 않는다. `위 질환은 없어요`는 네 선택지 중 해당 항목이 없다는 뜻이며, 아직 입력하지 않은 상태와 구분한다. 진료정보에서 얻은 질환 후보도 지우지 않는다.

`내정보질환매핑`은 **MAPPED 3개**(고혈압, 당뇨병, 이상지질혈증)와 **SAFETY_ONLY 1개**(만성 신장질환)로 고정한다. 앞의 3개는 연결 축과 금지 성격을 적용한다. 신장질환은 새 목표 축 없이 섭취량 증감·수분 목표를 제외하는 안전 조건으로만 사용한다. 나머지 질환은 수동 선택지에 표시하거나 수동 코드로 저장하지 않는다. 진료정보 경로의 별도 질환 규칙은 유지한다.

목표 축의 출처 우선순위는 **직접 선택 → 사용자 확인을 거친 진료정보 → 3개월 이내 건강검진 신호 → 일반 식이 질문**이다. 같은 질환이 직접 선택과 진료정보에 모두 있으면 직접 선택 출처로 한 번만 반영한다. 서로 다른 질환이면 직접 선택 축을 먼저 시도하고 통과 후보가 없을 때 진료정보 축으로 넘어간다. 금지 성격은 우선순위와 관계없이 진료 후보와 직접 선택의 안전 조건을 모두 합친다. `위 질환은 없어요`는 직접 선택만 비우며 진료정보를 지우지 않는다.

자가 선택과 진료정보가 모순되면 두 출처를 모두 남기고 충돌로 표시한다. 수동 선택을 고치면 현재 **미완료 목표**를 안전 필터로 다시 고르고, 완료 목표와 과거 기록은 보존한다. 수동 선택은 `selection_order`를 저장한다. 같은 질환의 진료 기록이 여러 건이면 원본을 보존하고 최신 `effective_at` 상태 1건으로 집계한다. 통합 선택기는 직접 선택 축에 통과 후보가 없으면 진료정보, 유효 검진, 일반 질문 순서로 이동한다.

## 확정 구현 기준

| 항목 | 적용 상황 | v1.0.0 구현 기준 |
|---|---|---|
| 질환 확인 당일 질문 수 | 지방간 확인 뒤 공통 고정과 회전을 모두 물어 세 문항이 됨 | 식이는 세션당 최대 2개다. 확인 질문에 `USER_CONFIRMED`이면 해당 질환 회전, `DENIED`·`UNKNOWN`이면 공통 고정을 둘째로 낸다. 다른 질문은 조건상 생략한다. |
| 질환 확인 순서와 묶음 | 진료정보로 고혈압·이상지질혈증이 함께 들어와 무엇을 먼저 물을지 구현마다 달라짐. 이상지질혈증은 규칙이 `DX-03`·`DX-04` 둘인데 화면 표기가 같아 같은 질문이 두 번 나옴 | 확인 대기 질환을 `confirmation_label`로 묶는다. 표기가 같으면 한 묶음이고 한 번만 묻는다. 답 하나를 그 묶음의 모든 `rule_id`에 같은 상태로 기록한다. 순서는 `source_visit_date` 내림차순, 같거나 없으면 `rule_id` 오름차순이며 하루에 한 묶음만 낸다. 설정 `CFG-066` · 검증규칙 `V-47`·`V-48` |
| 목표 단계가 축 상태보다 빨리 오름 | 목표 완료는 매일 쌓이고(3일이면 상승) 질문 답은 그 축이 돌아올 때만 쌓인다(5일에 한 번). 그래서 답 2건으로 축이 아직 `관찰 중`인데 목표는 `도전`까지 올라간다. 반대로 `개선 필요`인 축에 가장 어려운 문구가 나가 실패와 하락을 반복한다 | 단계 상승에 두 조건을 더한다. **① 그 축이 `관찰 중`이면 올리지 않는다**(`CFG-068`). **② 축이 `개선 필요`이면 `기본`까지만 올린다**(`CFG-069`). 하락 규칙은 그대로다. 검증규칙 `V-42` |
| 지난 끼니와 세션 날짜 | 23일 03:00과 04:00에 모두 22일 저녁을 묻지만 세션은 서로 다름 | 응답은 `(user_id, meal_date, meal_type, question_id, question_version)`의 현재 유효 답 1건을 재사용한다. 목표와 완료 기록은 04:00 경계 `session_date`로 묶는다. |
| 식후 목표 | 22:00에 이미 끝난 저녁 행동을 목표로 냄 | 식후 후보는 10개다. 17:00~24:00에는 10개를 사용하고, `내일`이 들어간 8개는 `PRE_MIDNIGHT`로 제한해 00:00~04:00에는 기존 2개만 사용한다. 필터 통과 후 최근 30일 미노출 문구를 먼저 고르고, 모두 노출됐으면 마지막 노출이 가장 오래된 문구를 고른다. 후보가 없으면 `GUIDANCE_ONLY`다. |
| 모든 목표 문구 반복 | 계약에 없는 `display_order`가 전부 9999가 되어 ID가 가장 작은 문구만 계속 선택됨 | 일반·식후 목표 모두 사용자별 최근 30일 노출 이력을 적용한다. 현재 후보 중 미노출 문구를 먼저 쓰고, 모두 노출됐으면 마지막 노출이 가장 오래된 문구를 쓴다. `display_order`는 계약과 코드에서 사용하지 않는다. |
| 안내 상태의 단계 하락 | 안전·시간 조건을 통과한 문구가 없어 목표를 받지 못한 날도 미완료로 누적됨 | `GUIDANCE_ONLY`는 실행할 행동 목표가 아니므로 완료율 분모, 연속 미완료, 단계 상승·하락 계산에서 제외한다. `CREATED` 목표만 단계 계산에 사용한다. |
| 달력 조건 판정 | 토요일 01:00은 금요일 세션이므로 금요일 목표로 오판하거나, 명절 날짜를 추측함 | 평일·주말은 목표 행동의 현지 **달력 날짜**로 판정한다. 명절·연휴는 백엔드가 전달한 날짜 목록으로 판정하며 목록이 없으면 해당 문구를 제외한다. 세션 귀속 날짜와 분리한다. |
| 노출조건 상태 | 배달·편의점·회식 등 앱이 알 수 없는 상황값을 조건으로 사용함 | 상황 전용 문구 33개를 운영 세트에서 제외했다. 남은 143개는 모두 `READY`이며 시간대·평일·주말·명절·연휴만 자동 조건으로 사용한다. |
| 검진 신호와 목표 문구 | FPG·BP·TC·BMI의 축은 연결돼 있는데 전용 문구 ID가 없어 목표 전체가 막힘 | 기존 축 문구 풀을 재사용한다. FPG→Q01, BP→Q03, TC→Q07, BMI 25 이상→Q05. 통과 후보가 없으면 안내만 표시한다. 검진 데이터는 검진일로부터 달력 기준 3개월 이내인 경우만 식이 목표 선정에 사용한다. |

## 끼니별 식사 시각 단계

고정 질문(DIET-Q-00)에 `usual` · `less`로 답하면 다음 질문으로 넘어가기 전 같은 자리에서 시각 단계(점심·저녁 `DIET-Q-08`, 아침 `DIET-Q-09`)를 낸다. 질문 1개로 세어 식이 최대 3문항 · 전체 최대 5~6문항이고 진행 번호도 따로 센다. 어제 저녁(00~10시) · `very_little_or_skipped` · 연동 건강 앱에 그 끼니 기록이 있으면 `CONDITIONAL_SKIP`으로 두고 묻지 않는다(구현기준 R-11 · 검증규칙 V-55~V-58).

- 버튼은 `diet-meal-time-v1.0.0.mjs`의 `mealTimeOptions(instant, timeZone, mealType)`로 만든다. 답한 시각을 10분 단위로 내리고 1시간씩 거꾸로 세며, 점심은 14시 · 저녁은 21시를 넘으면 그 시각−1시간을 1번 선택지 시작으로 두고 질문 시작 시각(12시 · 17시) 아래로 내려가지 않는다. 아침은 7시 · 8시 고정이다(CFG-072~078).
- 응답은 `diet_answer`에 `option_code`와 함께 사용자가 본 구간(`option_window_start/end`)을 저장한다. 글자가 날마다 달라 구간이 없으면 뒤에서 범위를 다시 만들 수 없다.
- 추정은 `estimateMealTime`으로 `diet_meal_time` 1행을 만든다. 순서는 건강 앱 → 범위 안 걸음 멈춤 단서 1개 → (범위 비거나 120분 초과면 UNKNOWN) → 14일 평소 시각 → 범위 가운데. UNKNOWN은 지표 계산에서 빠질 뿐 점수를 깎지 않는다(CFG-079~082).
- 식후에 걸었는지는 걸음 기록으로 판정한다(구현기준 R-12 · CFG-086~088 · V-59). `judgePostMealAction`: 식사 시각이 모름이면 UNKNOWN → 관찰 시간 안 운동 기록 시작이면 COMPLETED → 걸음 기록이 없으면 UNKNOWN → 분당 20보 이상이 5분 넘게 이어지면 COMPLETED → 합계 300보 이상이면 COMPLETED → 그 밖에 NOT_COMPLETED. 지표 계산기에는 세 값만 넘기고 UNKNOWN은 분모에서 뺀다. 계산식 전달 문서 v7.0은 판정을 서비스 몫으로 두고 계산기는 세 값만 받는다.

## 데이터 검증

- 질문 8개(축)에 선택지 24개, 질환 확인 1개에 3개, 식사 시각 단계 2개(DIET-Q-08 · 09)에 6개가 연결돼 있으며 질문마다 정확히 3개다. 고아 선택지는 없다. 시각 단계 선택지는 점수가 없고 점심·저녁 글자는 답한 시각으로 만든다.
- 목표 문구 143개와 노출조건 143개가 버전 키로 일대일 연결된다. 전부 `READY`이며 식후 대상 10개도 모두 포함된다.
- **두 시트를 `phrase_id` + `phrase_version`으로 먼저 합친 뒤 선정 함수에 넘긴다.** 선정 조건이 한 줄 안에서 두 시트의 값을 함께 본다 — 상태는 목표문구에, 식후 허용과 노출 조건은 노출조건에 있다. 목표문구만 넘기면 식후 허용이 비어 후보가 0이 되고, 오류 없이 화면만 빈다.
- `diet-selection-v1.0.0.test.mjs`에서 경계 시각, 자정 이후 주말 판정, 명절·연휴 날짜 목록, 답변 재사용, 질환 확인 당일 최대 2문항 분기, 후보 없음, 식후 목표 최근 노출 순환을 확인한다.
- `diet-profile-condition-v1.0.0.test.mjs`에서 4개 선택 코드, 선택 순서, 수동 입력·미입력·해당 없음 구분, 직접 선택 우선·진료정보 최신 상태 집계, 같은 질환 중복 제거, 금지 성격 적용을 확인한다.
- `diet-goal-engine-v1.0.0.test.mjs`에서 달력 기준 검진 3개월 만료, 미래 검진 제외, 직접 선택 후보 소진 후 다음 출처 이동, 검진 만료 후 일반 질문 이동, 명절 날짜 판정, 일반 목표 문구 순환, 목표 단계 상승·하락, 엔진·JSON·데모의 공동 설정을 확인한다.
- `diet-meal-time-v1.0.0.test.mjs`에서 시각 단계를 묻는 조건(어제 저녁 · 못 먹거나 거름 · 건강 앱 기록 제외), 점심·저녁 버튼(10분 내림 · 1시간 간격 · 하한 12시 · 상한 14시/21시 · 자정 직전), 아침 고정 버튼, 추정 순서(건강 앱 → 걸음 단서 → 범위 상한 → 평소 시각 → 가운데), 오후 5시대 저녁의 빈 범위, 식후 행동 판정(이어 걷기 · 300보 · 운동 기록 · 모름)을 검사한다.
- 네 테스트 파일의 총 38개 검사가 통과한다.
- `maiReport_식이_참조설정데이터_v1.0.0.xlsx`에도 동일한 `내정보질환매핑` 4행과 열 정의를 넣었다. 개발 데이터계약의 매핑과 같은 코드를 사용한다.
- 통합 선택기와 시연 데모는 `diet-reference-config-v1.0.0.mjs`를 공동 원본으로 사용한다. 빌드 스크립트가 여기서 `diet-reference-v1.0.0.json`과 HTML 내장 데이터를 함께 생성하므로 우선순위·검진 유효기간·단계 코드가 따로 어긋나지 않는다. 30일 동안 완료 결과에 따라 입문·기본·도전 단계가 변한다.
