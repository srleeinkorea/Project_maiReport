1. 세 문서는 무엇이 다른가

문서답하는 질문단위읽는 사람예

기획서와 기능정의서는 한 문서다(2026-10-14). 기능마다 따로 있던 기능정의서 표는 그 기능 기획서의 「5. 규칙과 예외」 끝에 들어간다. 전체 기능정의서(maiReport_기능정의서_v1.0.0.html)는 모든 기능을 한눈에 보는 색인으로만 남기고, 새 규칙은 기획서에 먼저 쓴다.

세 문서를 화면마다 모두 만들지는 않는다. 기획서는 기능 단위로, 화면설계서는 상태와 이동이 복잡한 화면에만 둔다. 단순 화면(언어 · 약관 보기 · 로그아웃)은 화면정의서 한 장으로 끝낸다.

2. 세 문서가 공유하는 뼈대

모든 문서는 아래 다섯 덩어리를 같은 순서로 둔다. 가운데 「본문」만 문서 종류에 따라 장이 달라진다.

  1. 머리말 — 문서 종류 표시, 제목(탭 › 화면), 판 · 기준일 · 화면 ID · 관련 문서 링크. 첫 화면에서 「이게 어떤 문서인지」가 끝난다.
  2. 한눈에 보기 — 세 칸 요약. 이 문서가 다루는 것, 가장 중요한 결정 한 가지, 아직 정해지지 않은 것. 바쁜 사람은 여기까지만 읽는다.
  3. 본문 — 문서 종류별 고정 장(3절). 장 번호와 이름을 바꾸지 않는다. 해당 없는 장은 지우지 말고 「해당 없음」 한 줄을 둔다.
  4. 확인 필요 — 열린 질문과 결정 대기 목록. 표 하나: 질문 · 누가 정하나 · 기한 · 상태.
  5. 바뀐 것 — 판별 변경 이력. 날짜 · 판 · 무엇을 · 왜.

쓰는 법

  1. 처음 보는 사람 기준으로 쓴다. 내부 식별자 대신 한국어 이름을 쓰고, 꼭 필요하면 괄호 안에 한 번만 적는다.
  2. 규칙은 글 대신 예시로 설명한다. 「3일 연속 결식이면 안내」보다 「월 · 화 · 수 아침을 모두 거르면 목요일 아침에 안내가 뜬다」가 낫다.
  3. 색상 값과 글꼴은 적지 않는다. 디자이너 영역이다.
  4. 작성자 이름과 QA 체크포인트 장은 두지 않는다.
  5. 그림은 HTML 안에 넣는다(SVG 인라인 또는 프로토타입 캡처). 별도 SVG · PNG 파일로 두지 않는다.

3. 문서별 본문 장

기획서 본문 7장

  1. 배경과 목표 — 왜 지금 이 기능인가, 무엇이 좋아지나
  2. 대상과 상황 — 누가, 어떤 때에 쓰나(예시 인물 1~2명)
  3. 범위 — 이번에 하는 것 · 하지 않는 것
  4. 동작 방식 — 기능이 어떻게 굴러가는지, 예시로
  5. 규칙과 예외 — 표시 · 계산 · 잠금 등 정책과 예외 상황. 끝에 기능 정의 표(기능 · 언제 · 하는 일 · 어긋나면)를 둔다. 예전 기능정의서의 해당 기능 줄이 여기로 들어온다
  6. 데이터 — 어디서 받아 무엇을 저장하나(계약 문서 링크)
  7. 성공 기준 — 되었다고 볼 수 있는 조건

화면정의서 본문 6장

  1. 화면 개요 — 역할, 들어오는 길, 나가는 곳
  2. 화면 구성 — 위에서 아래로 영역 목록(그림과 번호)
  3. 영역별 정의 — 영역마다 요소 · 표시 규칙 · 데이터 출처(표)
  4. 상태별 표시 — 정상 · 데이터 없음 · 로딩 · 오류 · 미연동
  5. 동작 — 탭 · 스크롤 · 토글 등 이 화면 안에서의 반응
  6. 문구 — 화면에 쓰이는 글 전체(표)

화면설계서 본문 6장

  1. 흐름 개요 — 시작과 끝, 거치는 화면 목록
  2. 흐름도 — 상태와 이동을 한 장에(그림)
  3. 단계별 화면 — 단계마다 화면 그림 · 사용자가 하는 일 · 시스템이 하는 일 · 다음 단계
  4. 분기와 예외 — 실패 · 취소 · 재시도 · 권한 거부 등
  5. 데이터와 연동 — 단계마다 주고받는 것, 외부 연동이면 호출 순서
  6. 시나리오 — 처음부터 끝까지 예시 인물 하나로 따라가기

5. 작성 프롬프트 원용 — 디자인과 톤앤매너만 (2026-10-14)

사용자가 지정한 문서 작성 프롬프트에서 기획 문서가 가져오는 것은 [디자인]과 [표현(톤앤매너)] 두 가지뿐이다. 문서의 구조와 내용은 이 문서의 2 · 3절(공통 뼈대와 문서별 장, 기능 정의 표)에 충실하게 쓴다.
