01 · Overview

한눈에 보기

흐름의 출발점은 두 개임. 하나는 근거 문헌을 정리한 지식, 다른 하나는 앱으로 들어오는 사용자 데이터임. 둘은 상태 해석 단계에서 처음 만나고, 화면까지 나간 뒤에는 보정 피드백으로 다시 지식 쪽으로 돌아옴.

주 흐름 보조 · 피드백 지식에서 온 것 런타임 처리
읽는 법

왼쪽 세로선 두 개는 코칭 세트가 런타임으로 내려가는 경로임. 지표를 어떻게 계산할지(지표 정의·계산 신호)와 어떤 문구를 언제 띄울지(규칙·문구)가 같은 세트에서 나옴. 오른쪽 세로선은 3지표가 코칭 선택을 거치지 않고 화면으로 바로 가는 경로임 — 코칭 문구를 고르는 일과 하루를 해석해 보여주는 일은 서로 다른 산출물이기 때문임.

가운데 세로선은 수집에서 코칭 선택으로 곧장 내려가는 입력 경로임. 나이·확진 여부·확보된 입력 목록은 지표를 거치지 않고 그대로 쓰임 — 지표값만으로는 대상 필터(누구에게 보일 문구인가)와 노출 전제(필요한 입력이 있는가)를 판단할 수 없기 때문임(6장).

자동화 범위

사람이 손으로 유지보수하는 건 매핑표뿐임 — 지표 이름 짓기, 문구 묶음과 우선순위, 입력 카탈로그와 질문 문장, 운영상의 관찰 창, 출처 표기 문자열, 질환 상태 이름. 이 여섯 가지는 지식DB에 없는 정보라서 사람이 정해야 함.

나머지는 자동임. 지식DB에 문구나 근거가 추가되면 추출을 다시 돌리는 것만으로 반영되고, 매핑이 빠진 항목은 검증 단계에서 걸림.

교체 방식

문구나 임계가 바뀌면 5묶음 전체를 다시 전달함. 증분 갱신이 아니라 통째 교체임. 서비스는 버전만 확인하고 갈아끼움.

수집 원칙

디바이스 데이터가 기본 축임. 다만 watch를 쓰지 않는 사용자를 불리하게 만들지 않음 — watch가 있으면 더 자세히 해석하고, 없으면 낮은 해상도로 해석함.

기록은 점수 보너스가 아님. 식사 기록처럼 사용자가 직접 남긴 기록은 “기록했다”는 사실만으로 상태를 좋게 만들지 않음. 다만 특정 생활 순간을 알아보는 데 쓰임.

통과한 지표만

기준에 못 미친 지표는 넘기지 않음

넘기지 않는 값

계산할 수 없는 지표는 0이나 낮은 값으로 채우지 않고 목록에서 아예 뺌. 그러면 그 지표를 보는 규칙은 자동으로 걸리지 않음. “데이터가 없다”와 “값이 낮다”를 구분하기 위한 처리임.

대체 계산으로 만들어낸 값도 마찬가지임. 근거가 명시적으로 금지한 방식(예: 하루 총 걸음수를 일정 수로 나눠 활동 시간을 추정)으로 만든 값은 코칭 판정에서 제외함.

지금 계산 가능한 범위

05 · Three Indicators

상태 해석 ② 3지표 — 아키텍처 구조

같은 수집 데이터와 질문 답변을 세 관점으로 해석함. 사용자를 평가하거나 줄 세우는 점수가 아니라, 자기 생활을 이해하고 조절할 지점을 알아차리도록 돕는 해석 지표임. 기준은 계산식 전달 문서(LJH) 지표 가이드 V2 — 몸잠밥 v0.25 · 내실천 v1.2 승인, 일상결 v8.24 검토안(승인판 v8.19).

몸잠밥 지수 I1 · 오늘

“오늘 수면 · 움직임 · 식사가 권장 행동에 얼마나 가까운가?”
  • 수면 · 움직임 · 식사를 1/3씩 · 각 영역 최대 33.33점
  • 식사 = 식이 질문 60% + 식사량 30% + 식사시각 10%
  • 세 영역 자료가 다 모이기 전에는 「일부 기록」(단계 없음)
  • 현실적 하루 / 현실과 이상 사이 / 이상적 하루 (50 · 80)

내실천 지수 I2 · 오늘

“행동 기회에 실제로 반응했는가?”
  • 식사 후 · 기상 후 · 오래 앉음 중단 · 운동, 묶음마다 25점
  • 확인된 반응만 누적 · 알 수 없음은 0점으로 확정하지 않음
  • 하루 동안 쌓이기만 하고 내려가지 않음
  • 실천 초보 / 실천 중수 / 실천 고수 (25 · 75)

일상결 지수 I3 · 최근 28일

“최근 4주 생활이 어느 방향으로 변했나?”
  • 28일을 7일씩 W1~W4로 · 최근 주가 높을수록 양수
  • 움직임 · 지속성 · 운동 · 식후 행동 · 수면시각 · 식사시각 7항목
  • 28일 연속 기록 전에는 「준비 중」 · 하루 마감 후 갱신
  • 주춤기 / 유지기 / 탄력기 (Z ±0.05)

아키텍처 구조 — 데이터가 지나가는 다섯 층

왼쪽에서 오른쪽으로 데이터가 흐르고, 운영 · 검증 층이 판정 정책과 표시 경계를 계산 엔진 쪽으로 되돌려 줌. 상세 그림 · 계산기 · 시각별 화면은 「세지표 아키텍처 흐름도」에 있음.

시간대별로는 이렇게 보임 — 같은 하루를 시각마다

몸잠밥 · 내실천은 그 시각까지 들어온 기록으로 다시 계산하는 잠정값이고, 일상결은 하루 내내 전날 마감값임. 몸잠밥은 세 영역 기록이 다 모이기 전까지 「일부 기록」이라 단계가 붙지 않음.

세 지표의 관계

서로를 대신하지 않음. 잠이 짧아 몸잠밥 지수는 중간이어도 식후마다 실천했다면 내실천 지수는 높을 수 있고, 오늘은 이상적인 하루여도 최근 4주 동안 운동이 줄고 있다면 일상결 지수는 주춤기일 수 있음.

그래서 합산하거나 평균 내지 않음. 하나의 종합 점수로 만들면 각 지표가 답하는 질문이 흐려짐.

확인 대기

일상결 승인판(v8.19)과 검토안(v8.24) 중 출시 기준, 식이 질문 선택지별 점수표, 식후 · 기상 후 · 오래 앉음 행동 확인 Rule, 「일부 기록」 화면 표시 방법이 남아 있음(10장).

안전 게이트

일부 문구는 규칙 조건을 만족해도 바로 화면에 올리면 안 됨. 강도 높은 운동을 권하는 문구나 회복기 관련 문구가 여기 해당하고, 진단 확정 여부·심혈관 위험 평가·활동 가능 여부를 서비스가 별도로 확인한 뒤에만 노출함.

게이트 확인은 지식 쪽이 아니라 서비스 정책의 몫임. 코칭 세트는 “확인이 필요하다”는 표시만 넘겨줌.

노출 개수

묶음별 1건까지 걸러도 한 화면에 여러 건이 남을 수 있음. 그룹 간 노출 개수 제한은 서비스 정책으로 정함.

07 · Output

사용자 화면 출력

두 갈래가 여기서 다시 만남. 3지표는 하루를 이해하는 그림을, 코칭은 오늘 붙일 행동 하나를 담당함.

3지표 상태

  • 정밀 숫자가 아니라 이해 가능한 상태 표현
  • 세 지표를 나란히 — 합산값 없음
  • 관찰이 부족하면 “관찰 중”으로

하루 행동 1개

  • 규칙 평가를 통과한 문구
  • 낮은 마찰 — 지금 바로 할 수 있는 크기
  • 안전 게이트 통과분만

근거 표기

  • 어느 지침·근거에서 온 문구인지 요약 표기
  • 판정 로직은 이 값을 읽지 않음 — 표시·로그 전용
  • 문제가 생기면 원본까지 되짚을 수 있게 남김
표현 원칙

maiReport는 비의료기기 웰니스 서비스임. 진단·치료·질병위험예측으로 읽히는 언어를 쓰지 않고, 임상 판단은 의료진에게 미룸. 화면 문구는 평가하는 말투가 아니라 자기 이해를 돕는 말투여야 함.

우선 확보 순서

막힌 곳을 푸는 순서는 ① 나이(생년월일) → ② 활동 구간 샘플의 강도 구분 → ③ 확진 질환 → ④ 식사 시각 질문 → ⑤ 운동 세션임. ①②만 확보되면 일반 성인 대상 코칭이 한 번에 살아남.

반영 경로

지식DB에 문구나 근거가 추가·수정되면 추출을 다시 돌리는 것만으로 코칭 세트에 반영됨. 매핑이 빠진 항목은 검증 9종이 잡아내므로, 반쯤 반영된 세트가 서비스로 넘어가지 않음.

구분해 둘 것

보정은 학습이 아님. 계수를 데이터로 자동 갱신하는 구조를 지금 도입하지 않음. 사람이 값을 바꾸고, 바뀐 값은 버전으로 남음.
