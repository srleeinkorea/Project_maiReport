## 발견 사항

### QA-DIET-01 — 높음 / FAIL: 관찰 중인 축도 단계가 상승한다

근거: 계약 설정 CFG-068, 설정파라미터 CFG-068, 검증규칙 V-42. 구현점검 문서도 관찰 중에는 상승하지 않는다고 명시한다.

위치: diet-goal-engine-v1.0.0.mjs:47~63, recalculateAxisStage.

재현: 현재 INTRO, 축 상태 OBSERVING, 10월 4~6일 CREATED 목표 3건 완료, 기준일 10월 7일.

기대: INTRO 유지. 실제: BASE로 상승.

원인: 함수가 축 상태를 입력으로 받거나 확인하지 않는다. 재현 스크립트의 axisState는 누락된 컨텍스트를 보여주기 위해 전달한 값이며 현재 구현에서는 무시된다.

제안: 계약의 축 상태를 명시적인 입력으로 연결하고 상승 조건에 OBSERVING 제한을 반영한다. 상태 누락 시 정책도 정의한다. 하락은 기존 정책에 따라 별도로 유지한다.

### QA-DIET-02 — 높음 / FAIL: 개선 필요 축이 도전 단계로 상승한다

근거: 계약 CFG-069, V-42.

위치: diet-goal-engine-v1.0.0.mjs:47~63.

재현: QA-DIET-01과 같은 완료 기록, 현재 BASE, 축 상태 NEEDS_WORK.

기대: BASE 유지. 실제: CHALLENGE로 상승.

제안: NEEDS_WORK일 때 상승 상한을 BASE로 제한한다. QA-DIET-01과 같은 함수 변경으로 해결 가능하지만 별도 정책 검증 사례로 유지한다.

### QA-DIET-03 — 보통 / FAIL: 축 스냅샷의 필드와 상태 코드가 계약과 다르다

근거: 계약 필드정의 diet_axis_snapshot.state_code = OBSERVING, NEEDS_WORK, AVERAGE, GOOD, NULL.

위치: diet-goal-engine-v1.0.0.mjs:45,100. 구현은 status_code 및 IMPROVEMENT_NEEDED, NORMAL을 사용한다. 테스트도 이 구현 전용 필드로 작성되어 있다.

재현: GOOD / 유효답 1건인 Q01, NEEDS_WORK / 유효답 4건인 Q03을 계약 필드 state_code로 전달하면 Q01을 선택한다. status_code와 구현 전용 상태명으로 변환하면 Q03을 선택한다.

판정 범위: 계약 입력 그대로는 구현의 상태 순위 분기가 적용되지 않는다는 사실을 확인했다. 특정 상태를 우선하는 순위 자체가 승인 정책에 맞는지는 별도 확정이 필요하다. 계약 CFG-041은 질문 축을 유효답 수, 질문일, ID 순서로 정렬한다고 설명하므로 임의로 상태 우선순위를 정답으로 삼으면 안 된다.

제안: 계약 필드로 통일하거나 변환 어댑터를 명시한다. 질문 축 선정과 목표 후보 fallback의 순위를 구분해 계약과 대조한다.

### QA-DIET-04 — 높음 / 정적 불일치: 그날 회전 질문 축을 목표 선정에 연결하지 않는다

근거: 계약 구현기준 R-03, 검증규칙 V-39는 그날 회전 질문의 축을 우선 사용하고, 그 축에 통과 문구가 없을 때만 직접 선택 → 확인된 진료정보 → 유효 검진 → 일반으로 이동하도록 규정한다.

위치: diet-goal-engine-v1.0.0.mjs:87~120. selectDietGoal은 그날 선택된 회전 질문 ID를 입력으로 받지 않으며, 질환 연결 축부터 독립적으로 후보 목록을 생성한다.

영향: 일반 질문을 내는 날에도 연결 질환 축이 우선되어 질문과 목표 축이 달라질 수 있다. 기존 테스트는 출처별 fallback만 검증하므로 이 계약 조건을 증명하지 못한다.

제안: 그날 질문 선정 결과를 목표 엔진에 전달하고 해당 축의 통과 후보를 먼저 검사한다. 해당 축에 후보가 있을 때와 없을 때를 각각 검증한다.

문서 보완: 구현점검 문서는 출처 우선순위만 설명하고 질문 축 우선 조건을 생략한다. 계약 R-09 비고의 ‘목표 축과 따로 계산한다’는 설명도 독립된 선정 절차를 뜻하는지 결과 축까지 달라도 되는지를 분명히 해야 한다. R-03 및 V-39는 결과 축 일치를 명시한다.
